# pay-system 功能点编码流程

执行角色：主代理 `lead` 只做编排、核验和 Git，不写代码；本流程的编码部分（§1–§9、§11 的报告编写）由 `coder` 子代理执行。`coder` 遇到“告诉用户”“等用户确认”“向用户汇报”时，把内容写进最终回复交给 `lead` 转达；§10 的提交与推送由 `lead` 执行。定义见 `.opencode/agents/`。

一次只推进一个功能点。下文的“需求”指 `docs/02-requirements.md`，“约定”指 `docs/03-conventions.md`，“接口”指 `docs/05-api.md`，“表结构”指 `docs/database.md`。路径均相对仓库根目录。

## 1. 领取

1. 在需求 §3 总表找到功能点，确认状态为 `TODO` 或 `DOING`。
2. 检查“依赖”列中的功能点全部为 `DONE`。有未完成的依赖时停止，告诉用户缺哪些，不要顺手实现依赖。
3. 把 §3 中该功能点状态改为 `DOING`。

## 2. 读规则

按顺序读完再动手，不凭记忆：

1. 需求 §4 中该功能点的完整小节：头部的优先级、里程碑、依赖、表，以及“说明”“规则”“验收”。
2. 涉及资金变动：需求 §2.5（账户类型、分录规则、资金不变量）。
3. 小节中引用到的约定章节：单号前缀 §2、金额 §3、时间 §4、错误码与 `fail_code` §5、幂等/状态/事务 §6、命名 §7、配置项 §8。
4. 涉及接口：接口文档中对应接口的字段、错误码、示例；涉及签名：接口 §3。
5. “表”中列出的每张表在表结构文档中的字段、索引、约束。
6. `docs/06-flows.md` §1 覆盖矩阵中该功能点对应的状态机、泳道图、控制流图；测试应覆盖控制流图的每个出口。图与需求冲突时以需求为准，并同步修图。
7. 同模块已有代码的写法（目录结构、错误处理、测试组织），新代码与之保持一致。

发现规则缺失、矛盾或无法实现时：

- 文字澄清、补充显而易见的细节：直接改文档，在对应变更记录中登记，告诉用户改了什么。
- 改变业务规则、资金流向、接口兼容性、表结构、错误码语义：停下，说明问题和建议方案，等用户确认后先改文档再写代码。

## 3. 计划

动手前给用户一份简短计划：

- 要新建或修改的文件。
- 验收条目到测试的映射：每条验收对应哪个测试函数、单元测试还是集成测试。
- 需要同步的文档（表结构、接口、约定、配置、指标、故障点）。

计划与需求一致时直接继续，不必等待确认；偏离需求时先征求确认。

## 4. 先写测试

1. 每条“验收”至少一个自动化测试，测试函数上方注释功能点与条目：`// ACC-03 验收 3：1000 goroutine 并发扣款`。
2. 位置：单元测试与被测代码同包；需要 MySQL、Redis、Kafka 的集成测试加 `//go:build integration`；端到端测试在 `test/e2e/`，加 `//go:build e2e`。
3. 写法：
   - 表驱动；用 `clock.Fake` 控制时间，不依赖真实时间。
   - 禁止用 `time.Sleep` 等待异步结果，改为带超时的轮询断言。
   - 并发测试带 `-race` 运行，并发度不低于验收要求。
   - 涉及资金变动的测试，结束时调用 `CheckBalance` 全量核对（两个分片，转账类测试在全部终态后用 `expect_quiescent = true`）；ACC-10 完成前用 SQL 断言代替（见需求 §0.3）。
   - 签名相关测试必须覆盖接口 §3.7 的测试向量。
   - 集成测试用 testcontainers，或复用 `TEST_MYSQL_DSN`；每个测试包使用独立 schema，互不依赖执行顺序。
4. 运行测试，确认因为“功能未实现”而失败（新 API 未定义导致的编译失败也算），而不是因为测试本身写错。

## 5. 实现

分层与依赖：

- 服务内分 `handler`（协议转换）→ `biz`（业务规则）→ `dal`（数据访问）；`biz` 只依赖接口，便于替换为假实现。
- 服务之间只通过 RPC 或事件交互，禁止 import 其他服务的包，禁止访问其他服务的 schema。
- `kitex_gen/` 是生成代码，不手改；改 IDL 后执行 `make gen`。IDL 只增不删，新增字段 `optional`。

资金与状态：

- 金额只用 `money.Amount`（int64，分），禁止浮点数；手续费按约定 §3 计算。
- 状态只通过 CAS 更新：`WHERE <主键> AND status = ?`，同时 `version = version + 1`；影响行数为 0 时按约定 §6.2 重新读取判断。
- 写操作必须有幂等键（约定 §2.4）；唯一索引冲突（1062）走幂等分支，不当作错误抛出。
- 余额变更使用条件更新（如 `available >= ?`），不先查后改。
- 终态不可变。

数据库：

- sqlx + 手写 SQL，只用参数化查询，禁止拼接用户输入。
- 事务统一用 `dbx.WithTx`；事务内禁止 RPC、HTTP、MQ 调用；同一事务锁多行按主键升序。
- 一个事务只访问一个账户分片（`ShardDB(shard)`），跨分片只能走协调者 + 幂等分支（约定 §6.3 第 6 条）。
- 带性能开关的功能点（需求 §4.12），先实现开关关闭时的基线路径并测试，再实现优化路径；两条路径用同一组验收测试。
- 需要发事件时，在同一事务内 `outbox.Add(tx, ...)`。
- 表结构变化只能新增迁移文件（约定 §7.2），不改已存在的迁移。

时间、ID、错误：

- 当前时间只来自注入的 `clock.Clock`，`biz` 和 `job` 包禁止 `time.Now()`。
- 单号只用 `(*idgen.Generator).NewNo(ctx, prefix)`，前缀必须已在约定 §2.2 登记。时钟回拨超过 5ms 时返回 `ErrClockRollback`，调用方映射为已有的 `10004`。
- 错误码只用 `pkg/errno` 中的定义；包装底层错误用 `%w`；对外不暴露内部错误细节。新错误码先登记约定 §5.2。

IO、并发、日志：

- 所有 IO 函数第一个参数是 `context.Context`，超时取值见需求 NFR-REL。
- 后台任务与 goroutine 遵守需求 §2.8 和 NFR-REL-05：panic 恢复并计数，进程退出时等待当前批次完成，多实例并发安全；并发聚合用 `errgroup`。
- 日志用 `slog`，字段名按约定 §7.5；密钥、签名、完整 DSN 等敏感字段不得出现在日志、错误信息、trace 属性中。
- 新指标按 OPS-03 登记；新故障注入点按 QA-01 登记，命名按约定 §7.4。

依赖：

- 新增第三方依赖使用固定版本，并在 `docs/01-tech-decisions.md` §2 登记理由。能用标准库或已有依赖解决的不新增。

注释：导出标识符写 Go doc 注释；资金逻辑中不直观的地方（为什么这样防重、为什么这个顺序）写一句原因，其余不加。

## 6. 同步文档

与代码同一次改动完成，不留到以后：

| 变化 | 要做的事 |
|---|---|
| 表结构 | 新增迁移 → 在 MySQL 8.4.11 上执行 up 和 down → 按 `database-schema-documentation` 技能更新表结构文档并运行校验脚本 |
| 接口字段、错误码、行为 | 按接口 §0.1 更新：文档版本、最后修改、§0.2 变更记录、§1 总览“最后修改”列 |
| 错误码、单号前缀、配置项、命名 | 登记到约定对应章节，并在约定 §9 记录 |
| 配置项 | 同步加入 `deploy/.env.example` |
| 业务规则澄清 | 改需求对应功能点，在需求 §8.2 记录；分支、状态或调用顺序变化时同步 `docs/06-flows.md` 对应的图，更新版本与 §6 变更记录，并渲染校验 |
| 技术取舍 | 记入 `docs/01-tech-decisions.md` |

## 7. 验证

按顺序执行，全部通过才能进入收尾。BASE-01 完成前 Makefile 不存在，用括号中的命令代替。

1. `gofmt -l .` 无输出。
2. `make lint`（`golangci-lint run --build-tags integration ./...`，同时检查集成测试文件）无告警。
3. `make test`（`go test -race ./...`）通过。
4. 涉及数据库、Redis、Kafka：`make test-integration`（`go test -race -tags integration ./...`）通过。
5. 改了 IDL：`make gen && git diff --exit-code kitex_gen`。
6. 涉及核心包（`service/*/biz`、`pkg/money`、`pkg/sign`、`pkg/idgen`、`pkg/outbox`）：`make cover`，覆盖率不低于 70%。
7. 改了 gateway 或服务的对外行为且环境已启动：用 `paycli` 手工走一遍相关接口。

某一步无法执行（缺工具、Docker 未启动等）时，如实说明原因和未覆盖的风险，不能当作通过。验证失败先修复再继续，同一方法失败两次后停下分析根因。

## 8. 自检

提交结果前逐条确认，涉及资金的功能点必须全部回答“是”：

- [ ] 每条写路径都有幂等键，重复请求不会重复记账、重复冻结、重复通知。
- [ ] 两个相同请求并发到达时，只有一个成功写入，另一个得到一致的结果。
- [ ] 在任意两步之间进程崩溃，数据停在可恢复的状态，且有补偿任务或查单能推进。
- [ ] 外部调用超时的结果视为“未知”，不当作失败处理。
- [ ] 错误码与接口文档一致，没有新增未登记的码。
- [ ] 日志和错误信息中没有敏感字段明文。
- [ ] 每个 IO 都有超时。

资金链路和性能类功能点（ACC、PAY、REF、TRF、MQ、OPT）由 `lead` 派 `reviewer` 子代理做只读审查，`coder` 处理它给出的问题。

## 9. 收尾

1. 对照需求 §0.3 完成定义逐条检查，全部满足才把 §3 中的状态改为 `DONE`；有未满足项时保持 `DOING`，并说明还差什么。
2. 在 `docs/04-dev-plan.md` 勾选该功能点。
3. 有值得讲的踩坑、性能数据、取舍时，记入 `docs/interview-notes.md`。
4. 向用户汇报（对话内的简短汇报，完整说明在 §11 的功能点报告中）：
   - 完成了什么，改了哪些文件。
   - 验收条目 → 测试函数的对应表。
   - 运行过的验证命令及结果；没能验证的部分和原因。
   - 同步过的文档。
5. 收尾完成后立即按 §10 提交这一部分，再按 §11 写报告并提交。不要询问是否提交，也不要把已完成的文件留成未跟踪或未暂存状态。

## 10. Git

每完成一部分就提交。一部分是指：一个功能点的代码与本次同步的文档、该功能点的报告，或与功能点无关的流程改动（`.opencode/`、`AGENTS.md`、`PROJECT_GOALS.md`）。

- 分支与提交信息按约定 §7.6，如 `feat/ACC-03-ledger-post`、`[ACC-03] add ledger post`。
- 做完就提交，不等用户再确认。代码和报告仍是两个提交：先提交代码，再按 §11 写报告，报告单独提交 `[<功能点>] add report`。流程改动单独提交，不混进功能点提交。
- 只暂存这一部分的文件。提交后运行 `git status`，这一部分不得再以未跟踪或已修改未提交的形式留在工作区。不提交 `deploy/.env`。
- 提交有误时，用新的提交改正，或用 `git revert` 回退。不把改正留在工作区，也不改写已有历史。
- 不使用 `--no-verify`、`--amend`、`push --force`、`reset --hard`，除非用户明确要求。
- 推送仍只在用户明确要求时执行。

## 11. 功能点报告

每个功能点的代码提交后出具一份报告，向没读过项目文档的人讲清技术原理和已完成内容。格式、写作规则、自检方法见 `.opencode/skills/pay-feature-dev/report-template.md`，写之前先读完。

1. 时机：代码提交成功后立即写，报告的“代码提交”一栏填真实的提交 hash 和提交信息（`git log` 获取）。用户自己提交、或需要补写和重写时，用 `/feature-report <功能点编号>`。
2. 位置：`docs/reports/<功能点>-<简述>.md`，并在 `docs/reports/README.md` 索引登记一行。
3. 内容来源：技术讲解来自本次实现和需求、约定、接口、表结构文档；验收对照、验证记录、性能数据只能来自本次实际运行的结果，没跑过的写“未验证”和原因。
4. 自检：资金链路和性能类功能点（ACC、PAY、REF、TRF、MQ、OPT）必须按模板 §6 由 `lead` 派 `report-checker` 子代理只读报告做可读性检查，`coder` 按反馈修改后再提交。
5. 提交：可读性自检通过后立即把报告与索引一起作为 `[<功能点>] add report` 提交，只暂存这两个文件。不要等用户确认，也不要把报告留成未跟踪文件。
6. 完成后在对话中告诉用户报告路径、两个提交的 hash，以及可读性自检提出并已修改的问题数。

## 12. 禁止事项

- 跳过测试直接实现，或为了让测试通过而修改验收标准。
- 一次改动混入多个功能点，或顺手重构无关代码。
- 在代码里写死错误码数字、单号前缀、配置默认值之外的魔法值。
- 修改已执行过的迁移文件、手改 `kitex_gen/`。
- 代码与需求、接口、表结构文档不一致却不更新文档。
- 代码提交后不出报告，或在报告中写入没有实际运行得到的数据。
- 一部分已经做完却不提交，或把已完成的文件留在未跟踪、未暂存状态。
