# 功能点报告模板

每个功能点的代码提交后，按本模板出具一份报告。流程见同目录 `SKILL.md` §11。

## 1. 读者与目标

读者：懂 Go、MySQL、HTTP 基础，但没读过本项目任何文档、也不了解支付业务的后端工程师。

目标：读者只看这一份报告，就能回答四个问题：

1. 这个功能点解决什么问题，不做会出什么事。
2. 方案的核心机制是什么，为什么选它而不是别的方案。
3. 怎么证明它是对的（并发、重复请求、崩溃、超时时会发生什么）。
4. 做完了哪些，还差哪些，怎么自己复现验证结果。

## 2. 写作规则

1. 自包含：正文不能用“见需求 TRF-03”“按约定 §6.2”代替解释。需要引用规则时，把规则内容用一两句话写出来，编号放在括号里作为出处，如“状态只能用 CAS 更新（约定 §6.2）”。文档路径只出现在“延伸阅读”中，读懂正文不依赖它们。
2. 术语先解释再使用：领域术语（冻结、分录、凭证、TCC、在途账户、空回滚、防悬挂……）、技术术语（CAS、outbox、幂等键、行锁……）和项目内缩写，第一次出现时用一句话解释，并收进术语表。
3. 用具体数字举例：金额同时写分和元，如“10000 分（100.00 元）”；并发场景写清几个请求、谁先谁后、每一步后数据库里是什么值。
4. 先结论后细节：每一节第一句话就是该节的结论。
5. 数据必须真实：报告里的数字、命令输出、覆盖率都来自本次实际运行，并写明运行环境。没有运行的写“未验证”和原因，不写“应该可以”“预计通过”。
6. 代码只摘关键部分：每段不超过 30 行，标注文件路径，片段前用一句话说明“这段代码在做什么、看哪里”。不粘贴整个文件。
7. 图优先：流程、时序、状态变化用 Mermaid 或 ASCII 图，单张图不超过 15 个节点；图下用一两句话解释。
8. 不写空话：“高性能”“健壮”“优雅”之类的形容词必须跟着数据或机制，否则删掉。
9. 中文书写，代码标识符、命令、表名、字段名保持原文并用反引号包裹。

篇幅参考：BASE、TL、DOC 等工程类功能点 1–2 页；ACC、PAY、REF、TRF、MQ、OPT 等资金链路或性能类功能点 3–6 页。宁可短而清楚，不为凑结构写空节；不适用的小节写“不涉及”加一句理由。

## 3. 文件位置与命名

- 路径：`docs/reports/<功能点>-<简述>.md`，简述与分支名一致，如 `docs/reports/ACC-03-ledger-post.md`。
- 一次提交包含多个功能点时，写一份报告，文件名用编号连写，如 `docs/reports/ACC-04_ACC-05-freeze.md`，正文按功能点分节。
- 同一功能点后续修复或补充时，在原报告末尾“修订记录”追加一节，不另起新文件。
- 每份报告在 `docs/reports/README.md` 索引中登记一行。

## 4. 标准背景段落

“背景”一节开头先放下面这段系统简介，再按当前进度修改“已完成”那一句。这样每份报告的读者都能先知道系统长什么样。

> pay-system 是一个用 Go 编写的小型支付后端，模拟商户收款、退款、商户间转账三条资金链路，重点在数据一致性和性能。系统由 5 个部分组成：gateway（对外 HTTP 入口，负责签名校验和限流）、payment（支付单、退款单、转账单的状态管理和流程推进）、account（账户余额与记账，数据按商户分到 2 个数据库分片）、channel-mock（模拟微信、支付宝这类外部支付渠道）、recon（对账，核对系统内外数据是否一致）。服务之间用 Kitex RPC 同步调用，或通过 Kafka 消息异步通知；数据存在 MySQL 8.4，Redis 用于防重放。所有金额用整数“分”表示，所有记账只追加不修改。当前已完成：<按进度填写，如“工程骨架与账户分片路由”>。

## 6. 可读性自检

报告写完后，由 `lead` 启动 `report-checker` 子代理（权限上只能读 `docs/reports/`），只告诉它报告路径，并要求：

> 只阅读 `<报告路径>` 这一个文件，不要读取仓库中的任何其他文件。假设你是没接触过这个项目和支付业务的后端工程师，回答：
> 1. 这个功能点解决什么问题？不做会怎样？
> 2. 方案的核心机制是什么？为什么不用其他方案？
> 3. 重复请求、并发冲突、进程崩溃时系统会怎样，依据是什么？
> 4. 列出所有你看不懂的术语、跳跃的推理、缺少前提的句子，并指出位置。

按第 4 题的反馈修改报告，直到它没有提出新的看不懂项；前三题的回答与报告本意不符的地方也要改。资金链路和性能类功能点（ACC、PAY、REF、TRF、MQ、OPT）必须做这一步；其他功能点可以省略。
